# Set up and run Kage (for coding agents)

You are setting up Kage for the person you work with. Kage lets them tag `@kage` in Slack, and a Claude Code session on this machine does the work and answers in the thread.

Do every step yourself. Ask the person only for the steps marked **Person**, because only a human can click in Slack or in the Claude admin page. When you need them, say exactly what to click, and wait.

Each step ends with a check. Go to the next step only when the check passes.

## Set it up

1. Install Kage. Skip this step if you already ran the install line.
   ```sh
   curl -fsSL https://raw.githubusercontent.com/aloki-alok/kage/main/install.sh | bash
   ```
   Check: it ends with `Coding agent: follow <folder>/CLAUDE.md from step 1`. Run every later command from that folder. If it names a missing tool, install it (macOS: `brew install node`; Claude Code: https://code.claude.com/docs/en/quickstart), then run the line again. If it ends with `Up to date`, Kage is set up already, so go to step 3.

2. **Person:** connect Slack in a terminal window. The tokens must never pass through you: do not ask for them in chat, and if the person pastes one anyway, tell them to regenerate it in Slack. Open the window:
   ```sh
   osascript -e "tell application \"Terminal\" to do script \"cd '$PWD' && ./setup.sh setup\"" -e 'tell application "Terminal" to activate'
   ```
   On Linux, ask them to run `kage setup` in a new terminal. Then tell the person what the window does:
   1. It asks for the name they tag in Slack. Enter keeps `kage`.
   2. It opens Slack with the app filled in and lists the clicks: **Next** and **Create**, an app-level token with the scope `connections:write`, then **Install App > Install to Workspace > Allow**. If Slack says the app needs approval, a workspace admin approves it once.
   3. They paste the three tokens into one hidden prompt, in any order. Kage then starts and waits for Slack.

   Check: ask the person to tell you when the window ends with `Connected to Slack. Tag @<name> in any thread to try it.` If it stops on an error, the line names the fix.

3. Prove it works.
   ```sh
   ./setup.sh doctor
   ```
   Check: the last line is `All good`. Every `FAIL` line names its fix. Do that fix, then run the doctor again. On Linux, if `loginctl show-user "$USER" -p Linger` prints `Linger=no`, ask the person to run `sudo loginctl enable-linger $USER`, so Kage also starts at boot with no login.

4. Tell the person to tag `@<name>` in any Slack thread. They get 🥷 when Kage picks the task up, then 🗡️ for a quick answer, 📜 when Kage waits on their reply, and ⚔️ when the task is done. A message that needed nothing, such as a thanks inside a thread, ends with 👍 in place of the 🥷. Each thread runs in its own Claude Code session.

## Run it

The install line puts `kage` on your PATH (in a git checkout, run `./setup.sh link` once). Then `kage help` lists every command and `kage help <command>` shows one with an example. `kage doctor` prints the command that fixes each problem: run it, run the printed fix, and repeat until `All good`. It also lists which model each scheduled job and kagelet uses, and whether `opencode` is installed. `kage doctor --fix` runs the fixes that touch only Kage's files (today, the token file's mode), then checks again. The hub also runs it every hour with `--fix`, and DMs you when a problem shows on two checks in a row, and when it clears.

| Task | Command |
|---|---|
| Health check | `kage doctor`, or `kage doctor --fix` |
| What happened while you were away | `kage` with no command: what Kage did since you last looked (replies, kagelet runs, lessons kept, spend), each question still waiting on you, and how many kagelets are on. |
| One look at the hub and every session | `kage status`: one line with the version the hub runs, how long it has run, today's spend and its schedules and its starts in the last 24 h by cause (updates, restarts, settings changes, crashes), with a warning only for a crash or a stop it cannot explain, then one line per connector (on or off, when it last heard something, and its failures in the past hour; Jev's calls and failures today), then each session, then each kagelet (when it last ran, when it runs next, its spend today), then where to look next |
| The live console (mouse or keys: `1` `2` `3` threads, kagelets and schedules tabs, `↑↓` or `j` `k` pick, `tab` switch pane, `⏎` open a thread's steps, `s` its schedules, `a` attach, `x` cut after you confirm, `/` search, `f` filter: every thread, running ones, or one connector or kagelets, named in the footer, `q` quit). Each thread row shows what it cost today, in the warning color at `top.threadCostBar` dollars or more. A bar on top names whatever waits on you, and charts at the bottom show turns in the last hour and spend by hour | `kage top` |
| Watch and fix kagelets | `kage top`, then `2`: each kagelet's state (on, paused, broken, or over cap when a cap is set), last run and report, next run, cost today against its 7-day daily average, and who made it. In that tab, `r` runs one now, `p` pauses it, `u` resumes it, `x` removes it after you confirm, `v` revokes the standing approval of each write tool that kagelet holds, taking that tool from every kagelet that got it with no card, and `h` lifts its deny holds (steps you said no to, which it may not ask about again for `kagelets.denyHoldDays`). The keys act through the hub, so they need Kage running. `kage logs <kagelet>` lists its last 20 runs, newest first: time, cost, its status (ok, failed, running, or paused for cost when a cap is set) and its report, then today's chains it was a step of (`a > b > c` and where it stopped) and its messages to and from other kagelets (queued, delivered, read or failed). |
| What Kage did and spent | `kage stats [days]` (7 by default, up to 30): spend and turns per day, spend per connector, tokens in and out with the share read from cache and by kind of thread (owner, teammate, kagelet, dream), spend per model (the model that cost the most in each turn, for turns recorded since the update that added it), hub starts in the last 24 h, runs and refusals, turn time (p50 and p90), and reports to the Kage repo (filed, seen again, by link, denied, capped, failed). Counts and money only, never what was said. `kage cost [days]` lists spend per thread, with the models its turns ran on. |
| Follow every step | `kage watch`, or `kage watch support` for threads whose place contains "support" |
| Work in a thread's session yourself | `kage attach '<link>'` with the thread's Slack link ("Copy link" on any message in it). Keep the quotes, because the link holds `?` and `&`. Or `kage attach <place>`. It takes the session at once: a turn in progress stops, as with Esc. New tasks for it wait until you quit. When several threads share a place, attach by the link, or by the key it lists. |
| Tell a thread something, as you | `kage tell <place> <message>`. Its session takes it after the current turn and answers in the thread. |
| The hub log | `kage logs` follows it live, like `tail -f`, merged with the steps of every session (tools, replies). `kage logs 200` prints the last 200 lines and exits. It holds each task that arrives (where, from the owner or not, new or resumed session), each post, cost, card, grant and run, and every connector and relay line. A tag that Kage refused shows as a `dropped` line with the thread, the sender and the reason. |
| Apply a settings change | Edit `~/.config/kage/config.json`, or run `kage set <key> <value>`. Kage watches the file. A change to `people` (who may tag Kage) applies at once and cuts no session. Any other key restarts Kage by itself once every session is quiet. A wrong file is refused: Kage keeps the last good settings and DMs you the bad key. `kage reload` checks now and names what it applied or what waits for the restart. A change to `harness.runtime`, `harness.route` or `harness.memory` is safest with `kage stop`, then `kage start`. |
| See a usage-limit pause | `kage status` and `kage list` say when Claude's usage limit paused Kage, when it resets, and how many messages are held. Each thread got one line about it. Held messages run by themselves at the reset, or as soon as the limit lifts early: each new message, yours or a teammate's, tries at once (one at a time), and if it gets through, the pause ends and every held message runs. If the limit is still on, it is held with the rest. |
| Stop one thread | `kage stop '<link>'` or `kage stop <place>` ends that thread's session once its turn ends, and `--now` cuts it. In Slack, `@kage stop` or `@kage stop now` in the thread does the same: the owner anywhere, a teammate only in a thread their task started. Its schedules keep running, and the next tag starts it again. |
| Stop or restart | `kage stop` or `kage restart`. New messages wait, and it acts once every running turn ends, naming each thread it waits on. New messages run after a restart. `--cut-running` acts now and names what it cuts. A stop stays down until `kage start`. |
| Stop it starting by itself | `kage service off`, and `kage service on` to undo it. |
| Give sessions shell exports | Put them in `~/.config/kage/session.env` (mode 600), then `kage restart`. Every session can print them. To keep a key out of sessions, name it in `sessionKeys` (docs/settings.md, "Keys that stay out of sessions"). |
| Let one teammate-started thread use the SSM relay | `kage relay allow <place or key>`, `kage relay deny <same>`, `kage relay list`. The thread gets `KAGE_SSM_TOKEN` at its next session start (docs/settings.md, "ssh to hosts behind AWS SSM"). |
| See what Kage learned from your yeses | `kage trust list` shows each line: one teammate, one kind of step, one reach. `kage trust revoke <id>` takes a line back. Money, deletes, outside sends, production deploys and writes, a production shell, the SSM relay, secrets and product calls always ask. `trust.mode` is `shadow` by default: it changes nothing until you set `on` (docs/settings.md, "Trust record"). |
| Let a teammate tag it | `kage add <mention, member id, email, name or @handle>`. If it lists two people, ask which one. `kage remove <same>` takes them off, and `kage list` shows who is listed. The change applies at once, with no restart. To let one teammate use the owner's claude.ai connectors and other MCP tools (for a team that shares one Claude account), run `kage add <same> --trusted`, and `--not-trusted` to undo it. Their agents follow them. Secrets, the owner's memory, the owner's browser, Kage's owner-only tools and one-way steps stay as for any teammate. |
| Let a teammate's agent tag it | `kage add <app id or a pasted mention of the agent> <its owner>`. With the mention, Kage also saves the agent's tag, and tags the agent only on a reply it must read (the answer to its ask, or a question to it), never on an ack or thanks. An agent that posts as its own bot user (not with its owner's token) is heard only when added by its mention, because the saved tag proves which bot posted. An agent gets at most 20 turns a minute and 4 in a row in one thread. The owner is a person, or a listed agent's app id. It adds the person too. Removing a person removes their agents. To stop an agent that always answers from replying to acks, add `jevKey` (docs/settings.md, "Agent replies"). An agent owned by a listed teammate runs with that teammate's access, never the owner's, and approves nothing. An agent listed with no owner may only read and answer: every other tool is refused, with no approval card. `kage list` shows each agent under its owner with its access. |
| See and switch connectors | `kage connect` lists GitHub, Chrome, email, voice, WhatsApp, the meeting bot and SMS: on, off, or unset with the settings still missing, and the one step left. `kage connect <name>` turns one on, and `kage connect <name> off` turns it off and names what stays outside Kage (a webhook, an AWS queue, the extension in Chrome). `kage doctor` names a connector left half set up. |
| Let Kage read the person's Chrome | `kage connect browser`. It opens `chrome://extensions` and a Finder window with the `extension` folder highlighted. **Person:** turn on Developer mode, then drag that folder onto the Extensions page. It pairs by itself, and Kage picks up the new token once its sessions are quiet. Run again, it changes nothing and names the reload click; `--reinstall` makes a new token and opens both again. Only if the toolbar icon asks for a token, run `kage connect browser --show-token`. Check: `kage doctor` shows `ok    Chrome extension connected (v<version>)`. After an update, the extension reloads itself when its folder holds a new version. If the doctor says it runs an older version, click reload on Kage in chrome://extensions. |
| Voice, calls, email, AFK, limits | Every setting, with its default, is in [docs/settings.md](docs/settings.md). |
| Run threads as tmux panes instead | Run `kage set harness.runtime tmux`, then `kage stop` and `kage start`. Each pane then shows a channels warning screen that the person confirms (README, "Run threads as tmux panes instead"). |
| Add missing Slack scopes | `kage slack upgrade`. An installed Slack app keeps the scopes of the manifest it was made from, so an older install may lack newer ones and fail with `missing_scope`. `kage doctor` names each missing scope, and Kage DMs the owner once per distinct missing set at start. The command asks once for a Slack app configuration token (Generate Token under Your App Configuration Tokens at api.slack.com/apps; it is never saved), reads the app's manifest, adds only the missing scopes, saves it back, and opens the app's install page. Every other setting stays. With no token, or one Slack refuses, it opens the manifest page and prints the exact JSON lines to paste instead. **Person:** paste the token, then click "Reinstall to Workspace" and Allow (Slack asks a person to consent, so this click stays). It waits until Slack shows the scopes. If Slack shows new tokens under Install App, run `kage save`. |
| Update Kage | `kage update` pulls the newest Kage now, and the hub restarts into it at its next quiet moment with no message held. `kage update --stable` moves to the latest release instead. It changes nothing when the checkout has local changes or commits. A git checkout on `main` also updates itself every 6 hours to the commit tagged `stable` on origin, and DMs you the old and new version (`kage set autoUpdate false` stops it). With no `stable` tag, it does not update, and `kage doctor` says so. A release is a `vX.Y.Z` tag with a GitHub Release, and `stable` sits on it. The repo owner's own hub makes it by itself, checking hourly, after the commit has run on that hub for 24 hours (a change to docs or tests alone does not restart the clock) with `kage doctor` at `All good` and no crash-loop DM (`kage release` does it at once, and `--dry-run` shows the version and notes). Releases are not signed yet (#58). The install line makes one when git is installed, and run again it turns an older install into one. `kage doctor` says when an install cannot update itself. Otherwise run the install line again (`curl -fsSL https://raw.githubusercontent.com/aloki-alok/kage/main/install.sh | bash`), or `git pull` in a git checkout. A `git pull` moves the checkout past `stable`, so auto-update then waits until the tag catches up. The hub restarts into the new code by itself once every session is quiet and no usage-limit pause is on. A session cut by a restart resumes its conversation on its next task. `kage --version` shows the code on disk, and `kage status` and `kage doctor` show the version the hub runs. |

Never run `kage stop` or `kage restart` from inside a Kage session: it would end that session too, so the command refuses. The person runs it in their own terminal.

Settings are in `~/.config/kage/config.json`. The tokens are in `~/.config/kage/secrets.json` (mode 600). Never print the token file, copy it or commit it. The same goes for `~/.config/kage/owner.key` (mode 600): the `kage` commands send it so the hub knows they come from the owner's terminal. An old `env` file becomes `config.json` and `secrets.json` on the first start of this version, and the old file is kept as `env.imported-<time>` for 7 days. A `config.json` that still keeps teammates, trusted people and teammate emails in three lists is rewritten once into the one `people.teammates` list. Each email moves onto the listed Slack user that Slack says owns it, and the old file is kept as `config.json.before-tidy-<time>` for 7 days.
